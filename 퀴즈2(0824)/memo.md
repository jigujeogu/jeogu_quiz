# 스탠바이미1 장시간 행사 운영 최적화 가이드

**작성일:** 2026-08-24

**대상 기기:** LG 스탠바이미 1세대 27인치(27ART10 계열, webOS)

**현재 분석 대상:** 전체 퀴즈 중 일부 구간인 `screen1.html`, `screen2.html`

**향후 구조:** 별도로 존재하는 전체 버전 퀴즈 페이지에 현재 두 화면을 통합할 예정

**운영 조건:** 행사장에서 수 시간 동안 연속 실행 및 반복 체험
**최종 목표:** 단발성 시연이 아니라 장시간 실행 중에도 끊김, 누적 메모리 증가, 앱 재시작, 네트워크 의존 문제 없이 안정적으로 동작

---

## 1. 현재 상태에 대한 결론

현재 코드는 전체 퀴즈의 일부 구간이며, 이 두 화면만 일반적으로 1회 실행하는 조건에서는 충분히 최적화된 편이다.

- 무거운 캐러셀 아이콘과 퀴즈 원형 아이콘은 PNG로 교체됨
- `shopping_mall.svg` 대신 PNG가 사용됨
- 주요 이동 애니메이션은 `translate3d()`와 GPU 합성 레이어를 사용함
- 할인 타이머의 DOM 갱신 횟수는 초당 100회에서 20회로 감소함
- 해결한 퀴즈 요소의 애니메이션은 정지함
- 컨페티 애니메이션은 파티클이 사라지면 종료됨

다만 행사장에서 전체 퀴즈에 통합된 상태로 수 시간 연속 실행하는 조건에서는 아직 최종 최적화와 실기기 검증이 필요하다. 특히 다음 항목은 단발 실행보다 장시간 운영에서 더 중요하다.

1. 대형 이미지의 디코딩 및 GPU 메모리 사용량
2. 완료 이후에도 계속 호출되는 타이머와 유지되는 합성 레이어
3. 화면이 가려졌거나 입력 대기 상태에서도 계속 도는 애니메이션
4. 퀴즈를 여러 번 반복할 때 상태와 파티클이 완전히 초기화되는지 여부
5. 외부 CDN 폰트에 대한 네트워크 의존성
6. webOS의 메모리 회수 및 장시간 실행 안정성
7. 전체 퀴즈로 진입하고 빠져나올 때 이벤트·타이머·DOM·GPU 리소스가 완전히 정리되는지 여부

LG webOS 개발 안내에서는 TV가 PC보다 제한된 환경임을 고려해 앱 메모리를 250MB 미만으로 유지하도록 권장한다. 행사 운영용으로는 순간적인 최대치뿐 아니라, 반복 실행할수록 메모리 사용량이 계속 증가하지 않는지도 확인해야 한다.

## 2. 현재 코드의 주요 부하 지점

### 2.1 `shopping_mall.png` 디코딩 메모리

**상태: 완료 (2026-08-24)**

Lanczos 필터로 실제 표시 해상도에 맞게 축소하고 기존 자산을 교체했다.

| 항목 | 변경 전 | 변경 후 |
|---|---:|---:|
| 해상도 | 2160×6092px | 1080×3046px |
| 파일 크기 | 약 811.3KB | 약 563.5KB |
| 예상 RGBA 디코딩 메모리 | 약 50.2MB | 약 12.55MB |

- 원본과 변경 후 이미지의 가로세로 비율이 동일하므로 기존 CSS 좌표와 오버레이 정렬은 유지됨
- 픽셀 형식 `Format32bppArgb` 유지
- 텍스트, 상품 카드, 색상과 외곽선 육안 검증 완료
- 예상 디코딩 메모리 약 37.65MB, 약 75% 절감
- 최종 통합본의 실제 GPU 메모리와 스크롤 프레임은 스탠바이미 실기기 소크 테스트에서 추가 확인

### 2.2 `screen1` 대형 쇼핑몰 로고

**상태: 완료 (2026-08-24)**

세 SVG가 순수 벡터가 아니라 Base64 비트맵을 둥근 사각형으로 클리핑한 구조임을 확인하고, 현재 표시 크기에 맞는 투명 PNG로 교체했다.

| 로고 | 기존 본체 표시 크기 | 최종 PNG 캔버스 | 파일 크기 |
|---|---:|---:|---:|
| SHEIN | 900×900px | 1260×1260px | 약 74.7KB |
| AliExpress | 990×990px | 1350×1350px | 약 126.4KB |
| Temu | 900×900px | 1260×1260px | 약 120.1KB |

- 각 PNG의 사방 180px 투명 여백에 기존 `drop-shadow(0 28px 45px)` 값을 사전 합성
- `screen1.html`의 실시간 CSS `drop-shadow` 제거
- 패딩만큼 요소 위치를 보정해 실제 로고 본체의 `left`, `bottom`, 크기와 회전 중심을 기존 값과 동일하게 유지
- 세 PNG의 투명 모서리, 그림자 알파, 이미지 디코딩과 육안 선명도 검증 완료
- 낙하 `animationend`에서 `will-change: auto` 및 `backface-visibility: visible`로 되돌려 영구 GPU 합성 레이어 해제
- 기존 SVG는 원본 소스 자산으로 남아 있지만 실행 화면에서는 더 이상 참조하지 않음
- 최종 통합본에서 낙하 순간 CPU·GPU 사용량과 프레임은 스탠바이미 실기기로 추가 측정

### 2.3 캐러셀 합성 레이어

`screen1` 캐러셀은 JavaScript 프레임 루프가 아니라 CSS `transform` 애니메이션을 사용하므로 구조는 적절하다. 다만 10개의 540px 아이콘이 하나의 긴 트랙으로 합성되며, 캐러셀이 표시된 이후 계속 움직인다.

**권장 작업:**

- 사용자가 다음 행동을 하지 않고 장시간 방치할 수 있다면 일정 시간 이후 캐러셀을 정지하는 운영 모드 검토
- 화면이 숨겨졌거나 다른 화면으로 이동하면 애니메이션을 `paused` 상태로 변경
- `visibilitychange` 이벤트로 백그라운드 상태에서 애니메이션과 타이머를 일시 정지
- 화면을 다시 표시할 때만 재개

현재 `screen1.html`과 `screen2.html`은 실제로 서로 이동하지 않는 독립 문서지만, 최종적으로는 별도로 존재하는 전체 퀴즈 페이지에 통합될 예정이다. 따라서 별도 HTML 이동이나 전체 새로고침을 전제로 최적화하면 안 된다. 전체 퀴즈가 단일 페이지 구조라면 이 구간을 단순히 숨기는 것으로 끝내지 말고, 구간 이탈 시 애니메이션·타이머·이벤트·Canvas를 해제하는 명시적인 종료 절차를 실행해야 한다.

### 2.4 `screen2` 할인 타이머

**상태: 완료 (2026-08-24)**

50ms마다 센티초 값을 직접 차감하던 구조를 실제 경과 시간 기반 계산으로 교체하고 인터벌 생명주기를 분리했다.

- `TIMER_DURATION_MS`, `TIMER_TICK_MS` 상수로 주기와 갱신 간격 명시
- `performance.now()`와 59초 모듈로 연산으로 남은 시간을 계산해 프레임 지연 및 브라우저 스로틀링에 따른 누적 오차 방지
- `timerIntervalId`를 저장하고 `startDiscountTimer()`, `stopDiscountTimer()`, `resetDiscountTimer()`로 시작·종료·초기화 분리
- 타이머 정답을 처음 발견하는 즉시 `clearInterval()` 실행
- `tickDiscountTimer()`에서도 `solved` 상태를 확인해 남은 인터벌을 자체 정리하는 방어 로직 유지
- `pagehide`에서 인터벌을 종료하고 `pageshow`에서 중복 여부와 해결 상태를 검사한 뒤 필요한 경우에만 재시작
- 기존과 동일한 50ms 표시 갱신 주기를 유지하되 변경된 문자열만 DOM에 반영
- 경계값 `00:59:00`, `00:58:95`, `00:00:05`, 59초 후 재시작 계산 검증 완료
- 전체 퀴즈 통합 시 구간 `reset()`에서는 `solved` 클래스 제거 후 `resetDiscountTimer()`를 호출해야 함

### 2.5 품절 카운트다운

품절 카운트다운은 2초마다 `setTimeout()`을 다시 등록하고, 해결되면 다음 타이머를 등록하지 않으므로 현재 구조는 비교적 안전하다.

다만 퀴즈 재시작 기능을 추가할 경우 기존 타임아웃이 남은 상태에서 새 타임아웃이 중복 생성되지 않도록 ID를 저장하고 명시적으로 정리해야 한다.

### 2.6 최종 컨페티

**상태: 완료 (2026-08-24)**

축하 화면은 유지하면서 컨페티 렌더링 부하와 종료 후 잔존 자원을 줄이도록 실행 상한과 공통 정리 함수를 적용했다.

- 파티클 수를 160개에서 120개로 축소해 파티클 업데이트·회전·Canvas draw 호출을 25% 감소
- `CONFETTI_MAX_DURATION_MS = 2500`으로 최대 실행 시간을 2.5초로 제한
- `performance.now()`와 RAF 프레임 시간을 비교해 프레임 속도와 관계없이 시간 상한 적용
- 멱등적인 `stopConfetti()`에서 예약 RAF 취소, `confettiAnimId = null`, 파티클 배열 비우기, Canvas 초기화와 숨김을 한 번에 처리
- 재실행 전, 자연 종료, 2.5초 초과, `pagehide`, Next 버튼 클릭 경로에서 동일한 정리 함수 호출
- 자연 종료 후에도 축하 팝업·오버레이·Next 버튼은 그대로 유지
- Next 버튼을 컨페티 도중 또는 종료 후 눌러도 중복 호출 없이 안전하게 정리
- 아직 연결되지 않은 다음 화면 이동은 구현하지 않고, 향후 버튼 핸들러의 `stopConfetti()` 다음 줄에서 상위 퀴즈 라우터를 호출하도록 위치 표시
- 기존 160개 생성 루프와 하드코딩된 개별 Canvas 종료 경로 제거 및 코드 구조 검증 완료

## 3. 장시간 운영과 전체 퀴즈 통합을 위해 필요한 공통 제어

### 3.1 페이지 가시성에 따른 일시 정지

`document.visibilityState`와 `visibilitychange`를 이용해 화면이 보이지 않을 때 다음 동작을 중단해야 한다.

- 캐러셀 애니메이션
- 마키 애니메이션
- 할인 배지 플로팅 애니메이션
- 품절 카운트다운
- 할인 타이머 인터벌
- 컨페티 `requestAnimationFrame`

화면을 다시 열면 현재 상태에 맞는 동작만 재개한다. 다만 `visibilitychange`는 브라우저나 앱 전체가 가려지는 상황만 감지한다. 전체 퀴즈 내부에서 다른 구간으로 이동하는 경우에는 상위 퀴즈 페이지가 별도로 현재 구간의 `pause()` 또는 `unmount()`를 호출해야 한다.

### 3.2 부분 퀴즈 생명주기와 재시작 정리 함수

현재 두 화면을 전체 퀴즈에 안전하게 합치려면 이 구간의 실행을 명시적으로 시작하고 끝낼 수 있어야 한다. 권장 인터페이스는 다음과 같다.

```text
mount(container, options)  화면 DOM 구성 및 최초 이벤트 등록
start()                    현재 구간의 타이머와 애니메이션 시작
pause()                    일시적인 화면 이탈 시 지속 작업 정지
resume()                   현재 상태에서 지속 작업 재개
reset()                    다음 참가자를 위해 이 구간 상태 초기화
unmount()                  이벤트, 타이머, Canvas, DOM 참조 완전 해제
```

정확한 함수명은 전체 퀴즈 구조에 맞춰 바꿀 수 있지만, 같은 역할의 생명주기는 반드시 필요하다. `mount()`가 여러 번 호출되어도 이벤트 리스너와 타이머가 중복 등록되지 않아야 한다.

행사에서는 한 참가자가 끝낸 뒤 다음 참가자가 바로 사용할 수 있어야 한다. `reset()`은 단순히 화면을 처음처럼 보이게 하는 것뿐 아니라 현재 구간의 실행 자원을 정리하고 초기 상태를 다시 구성해야 한다.

재시작 함수에서 정리할 대상:

- 모든 `setInterval` 및 `setTimeout`
- 컨페티 `requestAnimationFrame`
- Canvas 내용과 파티클 배열
- `foundItems`와 `activeId`
- `solved`, `quiz-active`, `pulse`, `show`, `bboing` 클래스
- 진행바 이미지와 위치
- 스크롤 위치
- 타이머 숫자와 품절 수량
- 오버레이 및 팝업 표시 상태
- 효과음 재생 위치
- 현재 구간에서 등록한 모든 이벤트 리스너
- DOM 요소를 가리키는 장기 참조

전체 페이지 `location.reload()`는 전체 퀴즈의 진행 상태와 다른 구간까지 초기화하므로 현재 구간의 기본 재시작 방법으로 사용하지 않는다. 정상적인 참가자 교체와 구간 이동은 `reset()`과 `unmount()`로 처리하고, 전체 앱 새로고침은 복구가 어려운 오류가 발생했을 때의 최후 수단으로만 사용한다.

### 3.3 전체 퀴즈 통합 시 충돌 방지

현재 두 HTML은 독립 문서이므로 전역 범위 사용과 범용 CSS 선택자가 허용되어 있다. 전체 퀴즈에 그대로 합치면 다음 충돌이 발생할 수 있다.

- 두 파일 모두 `const CANVAS_W`, `const CANVAS_H`, `const scene` 같은 전역 이름 사용
- `#scene`, `#overlay`, `#btn-next`처럼 전체 퀴즈의 다른 화면과 겹칠 수 있는 ID 사용
- `html`, `body`, `*` 스타일이 전체 퀴즈 페이지에 영향을 줌
- `@keyframes` 이름이 다른 구간과 겹칠 가능성
- 문서를 다시 표시할 때 `addEventListener()`가 중복 등록될 가능성
- 상위 퀴즈의 진행 상태와 현재 `foundItems` 상태가 서로 분리될 가능성

**권장 통합 원칙:**

- 현재 구간을 고유한 루트 컨테이너 아래로 한정
- CSS 선택자와 애니메이션 이름에 구간 전용 접두사 사용
- JavaScript를 ES module 또는 하나의 모듈/클로저로 감싸 전역 변수 제거
- 이벤트 등록 함수와 해제 함수를 한 쌍으로 관리
- 진행 결과는 상위 퀴즈에 콜백 또는 이벤트로 전달
- 다음 화면 이동은 현재 `btn-next` 내부에서 직접 결정하지 않고 상위 퀴즈 라우터에 요청
- 이미지와 사운드는 이 구간 진입 직전에 preload하고, 전체 퀴즈 시작 시 모든 대형 리소스를 한꺼번에 디코딩하지 않음
- 동일한 리소스의 중복 preload 및 중복 Audio 객체 생성을 방지

현재 `screen1`의 `enterScreen2()`는 실제 `screen2.html` 이동 함수가 아니라 첫 번째 문서 내부 연출 전환이므로, 전체 퀴즈 통합 시 실제 화면 라우팅 함수와 혼동되지 않도록 이름과 책임을 분리해야 한다.

### 3.4 유휴 상태 자동 복귀

참가자가 중간에 이탈할 가능성을 고려해야 한다.

권장 운영 정책:

- 마지막 터치 이후 2~5분 동안 입력이 없으면 상위 전체 퀴즈의 지정된 대기 화면으로 복귀
- 팝업이 열린 상태로 방치되어도 자동 복귀
- 현재 구간의 축하 화면은 10~30초 후 상위 퀴즈의 다음 구간 또는 지정 화면으로 이동
- 복귀 시 상위 라우터가 현재 구간의 `reset()` 또는 `unmount()` 실행

이 정책은 화면 번인보다도, 중간 상태로 방치되거나 애니메이션이 계속 실행되는 것을 방지하는 효과가 크다.

### 3.5 오류 복구

행사에서는 운영자가 개발자 도구를 확인하기 어렵기 때문에 자동 복구 전략이 필요하다.

권장 사항:

- 전역 `error` 및 `unhandledrejection` 이벤트 기록
- 현재 구간 오류는 상위 퀴즈에 전달하고, 가능하면 해당 구간만 `unmount()` 후 다시 진입
- 전체 앱 상태가 복구 불가능할 때만 유휴 상태에서 전체 페이지 새로고침
- 화면이 멈췄을 때 운영자가 쉽게 재시작할 수 있는 숨겨진 관리자 터치 영역 또는 단축 동작 제공
- 하루 운영 시작 전 브라우저 또는 앱을 한 번 완전히 재시작

자동 새로고침은 사용자 입력 중 발생하지 않도록 유휴 상태에서만 실행해야 한다.

## 6. 실기기 소크 테스트 계획

PC Chrome 테스트만으로는 충분하지 않다. webOS의 CPU, GPU, 메모리 회수 특성이 다르므로 실제 스탠바이미1에서 측정해야 한다.

### 6.1 사전 확인

- 스탠바이미 설정에서 webOS 버전 확인
- 최신 안정 펌웨어 적용 여부 확인
- 절전 모드, 화면 보호기, 자동 꺼짐 정책 확인
- 실제 행사와 동일한 세로 방향, 밝기, 네트워크 조건 사용
- 행사에서 사용할 것과 동일한 실행 방식으로 테스트

### 6.2 반복 시나리오

현재 두 화면만 반복해서는 통합 후 누적 문제를 발견할 수 없다. 다음 흐름을 전체 퀴즈 통합본에서 자동 또는 수동으로 최소 50~100회 반복한다.

1. 전체 퀴즈 시작 화면 진입
2. 현재 `screen1` 구간 이전의 다른 퀴즈 화면 진행
3. `screen1` 진입 후 타이핑 중 스킵
4. 캐러셀과 퀴즈 카드 표시
5. `screen2` 구간 진입
6. 위아래로 여러 번 빠르게 스크롤
7. 다크패턴 5개를 서로 다른 순서로 클릭
8. 팝업을 요소 재클릭과 오버레이 클릭 방식으로 각각 닫기
9. 컨페티와 현재 구간의 축하 화면 완료
10. 전체 퀴즈의 다음 구간 진행
11. 전체 퀴즈 완료 후 대기 화면 복귀
12. 다음 참가자 회차 반복

중간 이탈도 별도로 반복한다. `screen1` 타이핑 도중, `screen2` 스크롤 중, 정답 팝업이 열린 상태, 컨페티 실행 중에 다른 구간으로 이동한 뒤 다시 들어와 중복 애니메이션·이벤트·사운드가 발생하지 않는지 확인한다.

### 6.3 최소 운영 시간

- 1차 개발 테스트: 30분
- 2차 안정성 테스트: 4시간
- 최종 행사 리허설: 실제 행사 예상 최대 운영 시간 이상

행사가 8시간이라면 가능하면 8시간 이상 연속 실행한다. 기기를 껐다 켜지 않고 테스트해야 누적 문제를 확인할 수 있다.

### 6.4 측정 항목

LG webOS CLI 리소스 모니터, Web Inspector 또는 Beanviser를 사용한다.

- 앱 프로세스 메모리 사용량
- 시스템 전체 사용 가능 메모리
- 유휴 상태 CPU 사용률
- 스크롤 중 CPU 사용률
- 컨페티 실행 중 순간 CPU 사용률
- 프레임 드롭 및 긴 메인 스레드 작업
- 반복 횟수에 따른 메모리 증가 추세
- 이미지 디코딩 및 GPU 합성 경고

### 6.5 합격 기준

다음 조건을 모두 만족해야 행사 운영 가능 상태로 판단한다.

- webOS 권장 범위인 앱 메모리 250MB 미만 유지
- 반복 실행 후 메모리가 계속 우상향하지 않고 일정 범위로 돌아옴
- 4시간 이상 앱 강제 종료 또는 자동 재시작 없음
- 터치 입력 누락, 팝업 중복, 스크롤 잠금 고착 없음
- 퀴즈 재시작 후 이전 참가자의 상태가 남지 않음
- 현재 구간을 반복 진입해도 이벤트가 한 번만 실행되고 타이머 속도가 빨라지지 않음
- 현재 구간 이탈 후 캐러셀, 마키, 타이머, 컨페티가 백그라운드에서 계속 실행되지 않음
- 현재 구간 오류 또는 초기화가 전체 퀴즈의 다른 진행 상태를 손상하지 않음
- 다른 퀴즈 화면과 ID, CSS, 사운드 및 키보드·터치 이벤트 충돌이 없음
- 컨페티가 끝난 뒤 CPU 사용량이 유휴 수준으로 복귀
- 네트워크 단절 상태에서도 모든 핵심 화면과 폰트가 정상 표시
- 행사 운영자가 개발자 도구 없이 초기화할 수 있음

60fps는 목표로 삼되, 장시간 행사에서는 순간적인 한두 프레임보다 입력 반응, 메모리 안정성, 자동 복구가 더 중요한 합격 조건이다.

## 9. 최종 요약

현재 `screen1.html`과 `screen2.html`은 전체 퀴즈 중 일부 구간이다. 짧은 독립 시연용으로는 충분히 가볍지만, 수 시간 연속 행사 운영과 전체 퀴즈 통합을 위해서는 다음 다섯 가지가 핵심이다.

1. `shopping_mall.png` 디코딩 메모리 축소
2. 타이머, 애니메이션, GPU 레이어의 명시적인 시작·정지·정리
3. 참가자 교체를 위한 완전한 초기화 및 유휴 자동 복귀
4. 전체 퀴즈가 호출할 수 있는 구간 생명주기와 전역 충돌 방지
5. 실제 전체 퀴즈 통합본을 스탠바이미에서 최대 행사 시간 이상 소크 테스트

이 다섯 항목이 완료되고, 전체 퀴즈를 반복하는 동안 현재 구간을 드나들어도 메모리와 이벤트 수가 안정적으로 유지되는 것이 확인되어야 장시간 행사 운영에 충분히 최적화되었다고 판단할 수 있다.
